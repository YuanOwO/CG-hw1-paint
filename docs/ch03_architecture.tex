\section{系統架構與設計}
\label{sec:architecture}

\subsection{整體架構}

為了避免繪圖、事件處理與 OpenGL 呼叫全部集中在 GLUT callback 中，
程式將主要功能拆分為視窗管理、文件資料、繪圖工具與畫面渲染等部分，
整體架構如圖~\ref{fig:architecture} 所示。

\lstinline|Application| 負責建立與管理各個視窗，
\lstinline|PaintWindow| 則組合繪圖介面、選單、快捷鍵與目前的
\lstinline|Document|。
使用者在 Canvas 上完成一次操作後，產生的繪圖物件會交由
\lstinline|Document| 修改 \lstinline|Scene|；
顯示時再由 Renderer 讀取 \lstinline|Scene| 中的內容並繪製到畫面上。

這樣的分工讓使用者操作、文件資料與渲染流程彼此分開。
例如 Undo/Redo 只需要處理文件內容的修改，
Renderer 也不需要知道物件是透過哪一種工具建立的。

    \caption{繪圖程式的整體架構}

\subsection{Application 與 Window}

\lstinline|Application| 負責 FreeGLUT 的初始化，以及所有視窗的建立與生命週期管理。
除了主要的 \lstinline|PaintWindow| 外，
文字輸入、確認視窗與圖片輸出所使用的視窗也共用相同的管理方式。
各視窗類別的繼承關係與 \lstinline|Application| 的管理關係
如圖~\ref{fig:window-classes} 所示。

\begin{figure}[htbp]
    \centering
    \includegraphics[width=.7\textwidth]{docs/figures/ch03-window-classes.png}
    \caption{Application 與視窗類別關係}
    \label{fig:window-classes}
\end{figure}

FreeGLUT 使用 C-style callback，
因此無法直接將 callback 綁定到某一個 C++ 物件%
\footnote{Non-static member function 具有隱含的 \lstinline|this| 參數，
    其函式型別與 FreeGLUT 所要求的 callback signature 不相同。}。
為了解決這個問題，每個 \lstinline|Window| 建立時都會記錄自己的 GLUT window ID；
callback 發生後，再利用目前的 window ID 找回對應的
\lstinline|Window| instance，最後將輸入交給該視窗處理。

\lstinline|Menu| 的處理方式也類似。
FreeGLUT 的 menu callback 只提供整數 ID，
程式再透過這個 ID 找回對應的選單項目並執行其動作。

較完整的 callback routing、Modal Dialog 與多視窗生命週期
整理於附錄~\ref{app:gui}。


\subsection{Document、Scene 與 Scene Object}

\lstinline|Document| 代表一份繪圖文件，
其中保存檔案資訊、Canvas 尺寸、\lstinline|Scene| 與
\lstinline|CommandHistory|。
新增、刪除或清除繪圖內容時，
都會透過 \lstinline|Document| 修改，
而不是由繪圖工具直接操作 \lstinline|Scene|。

\lstinline|Scene| 則依照繪製順序保存所有繪圖物件。
目前主要分為 \lstinline|ShapeObject| 與 \lstinline|TextObject|：
前者用來表示 Point、Line、Rectangle、Ellipse、Path 與 Polygon，
後者則保存文字位置、UTF-8 字串與文字樣式。

繪圖工具在操作完成後只需要產生對應的 Scene Object，
再交由 \lstinline|Document| 建立 Command 並加入
\lstinline|Scene|。
因此 \lstinline|Scene| 本身只負責保存資料，
不需要知道 UI、工具或 OpenGL 的存在。

拖曳期間顯示的 draft 與 Select 的選取框則屬於暫時的互動狀態，
不會加入 \lstinline|Scene|。
只有當繪圖操作真正完成，或使用者確定刪除物件時，
才會產生對文件內容的修改，因此也不會在操作過程中產生多餘的 Undo 紀錄。

圖~\ref{fig:document-classes} 整理了 \lstinline|PaintWindow|、
\lstinline|Document| 與場景物件之間的擁有與繼承關係。

\subsection{Event 與 Input}

FreeGLUT 提供的 keyboard、mouse 與 motion callback
會先由 \lstinline|Window| 轉換成程式內部使用的 Event。
Event 中除了事件本身的資料外，
也包含目前的 keyboard 與 mouse state，
讓後續元件可以用一致的方式判斷滑鼠位置、按鍵與 Shift 等狀態。

滑鼠事件會先經過 hit test 找出對應的 Element。
若目前已有 Element 取得 mouse capture，
則事件會優先交給該 Element，
使拖曳操作即使暫時離開原本區域仍能正常收到 MouseUp。

因此工具本身不需要直接處理 GLUT 的原始 callback，
只需要回應整理過後的 Event。
Event bubbling、focus、mouse capture 與 shortcut matching
等細節則收錄於附錄~\ref{app:gui}。


\subsection{Command History 與 Undo/Redo}
\label{sec:command-history}

為了支援 Undo/Redo，
所有會修改文件內容的操作都會封裝成可復原的 Command。
目前新增、插入、移除物件與清空畫布等操作，
都會經由 \lstinline|CommandHistory| 執行。

執行新的 Command 後，該操作會加入 undo stack；
使用 Undo 時會復原這次修改，並將 Command 移到 redo stack；
Redo 則再次執行同一筆 Command。
若 Undo 後又執行新的操作，原本的 redo stack 便會被清除。

每筆紀錄另外保存操作前後的 state ID，
用來判斷目前文件是否仍與最近一次儲存的狀態相同。
移除物件時也會記錄它原本在 \lstinline|Scene| 中的位置，
因此 Undo 後可以恢復原來的前後層級。

\subsection{Rendering Pipeline}
\label{sec:rendering-pipeline}

當視窗需要重新顯示時，Window 會從 Root Element 開始走訪 Element tree，
並讓各個 Element 在自己的局部座標系中進行繪製。
當流程進入 Canvas 時，後續的繪圖工作會交由
\lstinline|CanvasRenderer| 處理。

Canvas 內的內容具有固定的前後順序。
最先繪製的是背景 Grid，接著按照 \lstinline|Scene| 中的物件順序
繪製已完成的圖形與文字；
工具尚未完成的 draft 會疊在正式內容上方，
最後才繪製 Select 工具的選取框。
因此畫面由底到頂的合成順序為：

\[
    \text{Grid}
    \;\rightarrow\;
    \text{Scene Objects}
    \;\rightarrow\;
    \text{Tool Draft}
    \;\rightarrow\;
    \text{Selection Overlay}.
\]

對於 \lstinline|Scene| 中的正式物件，
\lstinline|SceneRenderer| 會依照物件類型將繪製工作分派給不同的 Renderer。
\lstinline|ShapeRenderer| 負責幾何圖形的 Stroke 與 Fill，
而 \lstinline|TextRenderer| 則負責文字與 Glyph 的繪製，
最後再轉換成實際的 OpenGL 繪圖命令。

這樣的設計將「畫面內容的前後層級」與「不同物件的繪製方式」分開處理：
Canvas 決定各類內容的合成順序，
而各 Renderer 則只負責如何將指定物件畫到畫面上。
整體流程如圖~\ref{fig:render-pipeline} 所示。
